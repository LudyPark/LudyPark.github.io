Incident investigation · Kotlin / Spring Boot

Stopping repeated out-of-memory restarts

I reduced repeated alert work and moved external reporting out of the database transaction. Memory use settled and the service stopped restarting from OOM.

What was happening

A service kept running out of memory after deployment. Giving it more memory did not stop the growth. CPU use rose before memory, so I started by looking at the work the service was doing.

What I found

When two sources of device data disagreed, each incoming packet generated another alert for the same unresolved condition. The error-reporting SDK repeatedly serialized the attached data. Thread dumps helped me locate that work.

The alert work was inside a database transaction. Slow reporting kept transactions open longer, increased pressure on the connection pool, and left more incoming work waiting.

What I changed

I reduced how often the same unresolved condition could trigger an alert. I also moved external alert reporting outside the transaction so it no longer extended the database work.

Result and limit

After the change, memory use stabilized and the OOM restarts stopped. The fix addressed the repeated work and its transaction boundary.

This change did not guarantee alert delivery after a database commit. A process failure in between could lose an alert. Guaranteed delivery would need a durable handoff, such as an outbox; that was not part of this fix.

Feature development · Kotlin / Spring Boot

Adding tips across different payment flows

I designed and implemented the backend payment flow for tipping and rolled it out across supported regions.

The requirement

A rider could add a tip before or after the fare was charged. Payment providers supported different ways to hold, capture, and confirm funds. A tip could also use a different payment method from the fare.

How I split the flow

I chose the payment path based on timing and payment method. Capture is the step that collects a previously authorized amount.

Before fare capture
Include the tip in the final fare capture when it uses the same payment method and the provider supports that path.
After fare capture
Create a separate tip transaction because the fare has already been collected.
Different payment method
Create a separate transaction using the selected method.
Waiting for a callback
Keep the transaction in a processing state until the provider confirms the result.

Duplicate requests and fees

I used a per-ride idempotency key and a distributed lock to prevent repeated or overlapping requests from creating duplicate tip charges. The key identified the same operation; the lock controlled concurrent processing.

When the tip and fare were collected together, I excluded the tip from the platform-fee calculation. I also recorded the payment fee for the tip separately.

Result

The feature reached production across the supported regions. It handled both combined and separate payments, with fee records that kept tips distinct from the fare.

Related work: fare increases during a ride

For a provider that could not increase an existing payment hold, I compared replacing the full hold with adding a second hold for the extra fare. I implemented the second option and captured the holds separately at ride completion. Keeping the original hold in place limited the amount at risk to the fare increase.

Message processing · MQTT / Kubernetes

Making message processing work across service instances

I changed how incoming messages and outgoing commands were distributed. Adding instances no longer caused each instance to write the same incoming data.

Why adding instances failed

The service had two problems. Every instance received the same incoming MQTT messages, which caused duplicate database writes. Outgoing device commands could also reach an instance that did not hold the device's live connection.

Incoming messages

I moved incoming work to MQTT shared subscriptions so the broker could distribute messages across consumers. During a local proof of concept, the existing client path lost shared-subscription messages. I found that the newer library versions still used the same underlying client, so I replaced the MQTT integration with the HiveMQ client.

Outgoing commands

The live connection belonged to one service instance. A shared lookup could identify a connection, but it could not make the connection object available in another process.

I used a broadcast path for commands. Each instance received the command, and only the instance holding the connection sent it to the device. Incoming data and outgoing commands therefore used different distribution rules.

Result and trade-off

The changes removed duplicate writes caused by every instance processing the same incoming message. The service could share incoming work across instances on Kubernetes while still sending commands through the instance that held the connection.

Broadcasting makes every instance inspect each command, so that work grows with the number of instances. Shared subscriptions also do not guarantee exactly-once processing. These are separate limits from the duplicate delivery caused by the old subscription setup.

Cost investigation · AWS S3 / CloudTrail / Athena

Finding the queries behind rising S3 costs

I traced repeated storage requests to unused analytics schedules. Removing those schedules reduced recurring S3 API costs.

The first lead

List requests to a data-lake bucket had become expensive. A change to the data crawler looked like a possible explanation, but delayed billing made it hard to tell whether that change had helped.

How I checked it

I grouped CloudTrail records by user agent to see which tool made the requests. Athena accounted for most of them. I then compared query execution history with the request spikes and traced the activity back to scheduled dashboard queries.

What I changed

The schedules were no longer used, but they still scanned broad partition ranges. I stopped the unused schedules and checked the daily S3 API cost afterward. The cost fell.

The scope of this result was S3 API requests. It was not a reduction of the whole AWS bill.

Other work

Improving battery-level readings

I used field data to investigate large drops in the displayed battery level while driving. I removed cached helper packets from the measurements, used movement history to detect stops, and applied filtering suited to driving and stopped states. The display became more stable, and pricing used the latest stopped-state reading.

Building operations tools and mobile features

I built GraphQL APIs and admin screens for vehicle assignment and lifecycle management. I also maintained a React Native driver app, added promotion and pricing features, and kept its build and release pipeline running.

Maintaining shared review tools

I built a GitHub Actions workflow to keep review configuration in sync across repositories. Review prompts followed the repository's stack and the type of change, with separate checks for SQL and database migrations.

Earlier work: device integration and query tuning

I built a mobile SDK that connected BLE devices to the server through a phone, extending a platform that had only supported Wi-Fi devices. I also improved a slow reporting query by replacing nested subqueries with joins and changing its union structure.

PRODUCTION CASE STUDIES

How I reason about backend systems.

These are not side projects. They describe generalized production experience, the boundaries used to make systems safer, and the questions I use to test a design. A proposed redesign is labelled separately so it is never confused with shipped work. Details are deliberately generalized: no employer-specific system identifiers, source code, customer data, or non-public operating metrics are included.

IMPLEMENTED / VERIFIEDWork I built, operated, or investigated in production.
DESIGN DIRECTIONHow I would change a boundary when a case exposes a limitation.

01

PAYMENTS · TRANSACTION CORRECTNESS

Do not let an uncertain gateway response decide the customer state.

I worked on payment flows in a mobility platform where capture timing and gateway capabilities varied by payment method. The core decision was to model payment as a stateful workflow, not one request-response call.

Implemented / verified

  • Used explicit intermediate and terminal payment states rather than treating a timeout as failure.
  • Applied idempotent request handling around payment changes.
  • Processed callbacks and used a later inquiry path for unresolved transactions.
  • Supported a multi-region tipping payment rollout.

State ownership

The ride workflow owns the customer-facing change. The payment workflow owns the provider reference and transaction state. Callback and inquiry results are translated into internal transitions; they are not assumed to be reliable synchronous responses.

Cases the design must answer

Duplicate requestUse an idempotency key tied to the logical operation. A repeat returns the already-owned result instead of creating another provider operation.
Provider completed, response lostKeep the payment unresolved rather than declaring it failed. A timeout only ends local waiting; provider inquiry supplies the authoritative result later.
Duplicate or late callbackMatch the stable external reference and make terminal transitions idempotent, so a replay cannot double-capture or move a completed payment backward.
Retry / DLQ / idempotencyThey solve different risks: retry gives delivery another chance, a DLQ isolates unprocessable work, and idempotency makes repeated processing safe.

Design direction: a no-row concurrency race

A database lock cannot protect a payment-change row that does not exist yet. For a redesigned concurrent destination-change flow, I would atomically claim a state on the existing ride record, commit that short decision, and call the provider outside the database transaction. This is a redesign approach, not a claim about an already-shipped path.

Questions I use to test the design

  • What is the source of truth when authorization may have completed but the response was not received?
  • Which record is the concurrency anchor when a new payment row has not been created?
  • Why should an external provider call sit outside the database transaction?
  • When is it safe to make an intermediate payment state final?

Supporting artifact: a small executable Kotlin reference for idempotent requests, response-loss recovery, and query-only reconciliation. It supports the ideas above; it is not presented as a substitute for production experience. View on GitHub ↗

02

MOBILITY · IOT · EVENT PROCESSING

Scale message processing without pretending connection ownership is shared.

I worked across Kotlin/Spring systems supporting a high-volume mobility platform and a connected-device platform running on Kubernetes.

Implemented / verified

  • Worked across a distributed Kotlin/Spring service ecosystem.
  • Used broker-managed message distribution to scale inbound IoT work across consumers.
  • Used broker-mediated routing so the service instance responsible for a persistent device connection performed the final command delivery.

Ownership model

Inbound device messages and outbound vehicle commands have different paths. Consumers can share message load, but a persistent device connection belongs to one service instance. Treating that socket as globally reachable makes scaling appear to work until a command lands on the wrong replica.

Structure and failure modes

Inbound telemetryDevice → broker → distributed consumers → domain processing. Broker-managed distribution spreads work while preserving an explicit messaging boundary.
Outbound commandCommand service → broker-mediated routing → service instance that owns the connection → device. The final delivery is deliberately performed by the owner instance.
Device reconnectsThe new owner must become discoverable through the messaging path; stale local ownership cannot be treated as durable global state.
At-least-once deliveryAssume duplicates and lag. Domain processing needs an idempotent effect, an observable retry path, and a defined response when a consumer falls behind.

Questions I use to test the design

  • Why is adding more pods not sufficient to scale a connection-oriented service?
  • Where does connection ownership live, and how does another replica find it?
  • What happens when a command reaches a non-owning replica?
  • What makes an event consumer safe under duplicate delivery and delayed recovery?

03

RELIABILITY · CLOUD OPERATIONS

Follow production evidence until the bottleneck has a mechanism.

A restart loop labelled as an OOM is not automatically a memory-leak problem. I diagnosed one incident by tracing CPU behavior, thread activity, transaction time, and connection-pool pressure before choosing a fix.

Implemented / verified

  • Used runtime and thread evidence to distinguish active work from retained-memory hypotheses.
  • Reduced unnecessary repeated work and shortened the database transaction boundary.
  • Improved stability by removing a workload that amplified under pressure.
  • Reduced recurring cloud API cost after correlating usage events with scheduled workload.

Why the symptom was misleading

The useful question was not “what object leaked?” but “what work keeps building up?” Repeated operational work made each request more expensive. Longer transactions consumed constrained resources, and waiting work accumulated until the service became unstable.

Evidence chain and boundary change

ObservationCPU increased before memory. That directed the investigation toward active work and thread behavior before a heap-retention hypothesis.
MechanismRepeated downstream work increased transaction time, constrained resources were exhausted, and waiting work accumulated.
ChangeReduce the repeated work source and avoid holding database resources while waiting on an external dependency.
Trade-offMoving the external call after commit protects the transaction, but an alert can be missed after a successful commit unless delivery is made durable separately.
Cost verificationFor the cloud-cost investigation, I correlated usage events with scheduled workload, removed unused work, and rechecked cost rather than treating an initial drop as proof.

Questions I use to test the design

  • What evidence distinguishes active CPU-bound work from retained-memory growth?
  • How can a slow SDK call indirectly lead to a memory-related restart?
  • What reliability property is lost when side effects move outside a transaction?
  • How do you prove that a cost change is causal rather than coincidental?

INTERVIEW FRAMEWORK

Make the state, owner, and recovery path explicit.

For every design I try to name the source of truth, the side effect that can be repeated, the boundary that should be short-lived, and the evidence that would prove the diagnosis. That makes it possible to discuss both what shipped and what I would change next.

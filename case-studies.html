Feature delivery · Kotlin / Spring Boot

Adding tips across different payment flows

I implemented the backend payment paths for tipping, including the different provider operations required before and after the main ride payment.

Situation
One product action could be included with the main payment or need a separate provider operation, depending on timing and payment method.
My role
I owned the server-side payment paths, provider callback handling, and release support.
Key decision
Model timing, duplicate requests, provider confirmation, and accounting records as separate concerns.
Result
The feature was released across supported regions with distinct fare and tip records.

The decision was not simply “charge a tip”

If a user added a tip before the main payment was finalized, it could be included in that path. If the main payment had already completed, the tip required a separate provider operation. The backend had to select the correct path, avoid duplicate charges, and preserve a clear financial record.

What I implemented

I added the state checks and provider paths for both timing cases. A short-lived distributed lock reduced concurrent duplicate requests, while a database uniqueness constraint remained the final guard. Tip amounts and fees were recorded separately from the fare so later lookup and settlement did not have to infer their meaning from one combined amount.

What this demonstrates

For a payment feature, the visible UI action is only the start. The backend design has to state which operation is allowed in each state, what happens after an uncertain provider response, and where duplicate prevention ends.

Decision record: payment state, duplicate protection, and accounting

State determined the provider operation

The first branch was not a UI choice. Before the fare capture, a tip could join the fare only when the payment method and provider capability matched. After capture, the original authorization could no longer be changed, so the tip became an independent transaction. A callback-pending request remained in a processing state rather than being treated as a failure.

Why the lock was not the correctness boundary

The distributed lock reduced the chance that concurrent requests reached the provider at the same time. It was intentionally treated as a contention-control mechanism, not proof of uniqueness: a lock can expire or a process can fail. The durable database uniqueness rule remained the last guard against creating the same per-ride tip record twice.

Unknown provider outcome

A timeout means the client did not receive a response; it does not prove the provider did not accept the operation. Local state and provider state therefore progressed separately. When the outcome was uncertain, status lookup or reconciliation was required before deciding whether to retry or finalize the record.

Why the financial records stayed separate

Fare, tip, and their fees had different business meaning. Recording them separately made fee calculation and later support investigation deterministic instead of depending on reconstructing one combined amount downstream.

Payment authorization · Kotlin / Spring Boot

Handling a fare increase after the original authorization

A provider could not increase an existing authorization. I used a separate hold for only the additional amount, keeping the original ride payment outside the new failure path.

Situation
A destination or fare change could increase the final amount after the initial authorization had already been created.
My role
I compared the payment options and implemented the authorization and capture flow for the additional amount.
Key decision
Keep the original hold unchanged and create a separate hold only for the incremental fare.
Result
A failure in the additional authorization affected only the fare increase, not the original ride payment.

Constraint

The provider did not support increasing an existing payment hold. The backend needed to preserve the original authorization while still collecting a legitimate fare increase at settlement.

Options and decision

I compared replacing the full hold with adding a second hold for the difference. Replacing the original hold would put the whole authorized amount at risk if the new authorization failed. I chose a separate hold for only the difference, then captured each hold at settlement.

Failure boundary

The additional authorization and its capture were handled as their own payment path. A failure was isolated to the incremental amount so it did not turn the successful original payment into a broader ride-payment failure.

Technical note: why the smaller hold was safer

Replace the full hold

This could leave a single final authorization, but it would require releasing or replacing the original amount first. If the new authorization failed, the payment risk covered the entire fare rather than only the change.

Hold the difference separately

This creates two captures at settlement, which adds bookkeeping. In return, the original successful authorization remains intact and the failure scope is limited to the extra amount.

What still needs explicit handling

Provider responses can be uncertain, so the additional hold has its own confirmation and recovery path. The existence of two holds does not remove the need to reconcile provider state before deciding a final payment outcome.

Incident investigation · Kotlin / Spring Boot

Stopping repeated out-of-memory restarts

A service restarted from OOM every 3–5 minutes. Increasing memory did not help. I traced the repeating work, changed the transaction boundary, and the service stabilized at about 2.4 GB.

Situation
Memory continued growing beyond 10 GB after a deployment, even after increasing the allocated memory.
My role
I investigated the runtime behavior and implemented the error-handling change.
Key decision
Reduce repeated reporting work and move an external error-reporting call out of the database transaction.
Result
The 3–5 minute restart loop stopped; steady memory was about 2.4 GB.

Diagnosis

Resource size was not the cause: after the limit increased from 4 GB to 8 GB, memory still grew past 10 GB. A thread dump showed an error-reporting SDK recursively serializing attachment objects through reflection, with one path consuming CPU for tens of seconds.

That SDK call ran inside a transaction. The transaction grew from roughly 10 seconds to 30–40 seconds, which exhausted the connection pool. Incoming messages then waited in memory while the same failure path continued to create reporting work.

What I changed

I first reduced repeated reporting for the unresolved condition, then moved the external call outside the transaction. This shortened the transactional critical section and stopped coupling database connections to a slow third-party serialization path.

How I checked the result

After release, I watched for the previous restart pattern and memory growth rather than treating a successful deployment as proof. The restart loop did not return and the service settled at about 2.4 GB.

This fix did not make alert delivery durable after commit. A transactional outbox would be a separate improvement if delivery had to survive a process failure between the database commit and the external call.

Investigation record: from memory pressure to the work creating it

Evidence chain

  • Increasing the memory limit did not change the growth pattern, so capacity was not the root cause.
  • Thread dumps showed sustained CPU time in recursive object serialization performed by the reporting SDK.
  • The external call held a transaction open long enough to consume pooled database connections.
  • Once the pool was constrained, incoming work accumulated in memory and the original failure path generated more reporting work.

Decision criterion

I did not optimize the serializer because the immediate incident was amplified by two observed conditions: repeated reports for an unresolved error and third-party work inside the transactional critical section. The released change removed those amplifiers before considering a deeper SDK-level change.

Transaction boundary

The transaction needed to protect the database update, not wait on a networked SDK whose latency and object traversal were outside the database's control. Moving the call out reduced connection hold time and kept rollback semantics scoped to the database work.

Known limitation

After commit, a process failure can still prevent the external report. A transactional outbox would add durable handoff, but that was a separate delivery guarantee and was not claimed by this incident fix.

Message processing · MQTT / Kubernetes

Making message processing work across service instances

When a service moved from one pod to two, both pods wrote the same incoming device data. I separated incoming work distribution from live-connection ownership so the service could scale without duplicate writes.

Situation
One service ingested device messages and also held TCP connections used to send commands. With two replicas, one message was processed twice.
My role
I redesigned the client and routing paths for incoming messages and outgoing commands.
Key decision
Use broker-side shared subscriptions for ingestion; use fanout only for a command that must reach the process holding the live socket.
Result
Adding a second instance no longer made each instance persist the same incoming data.

What made the change non-trivial

The two flows looked similar but had different ownership rules. Incoming telemetry is work that one consumer should handle. An outgoing command has to be sent through a specific process-local socket; the message broker cannot own that socket for the application.

What I changed

I moved incoming consumption to an MQTT shared subscription so the broker assigns a message to one eligible consumer. For commands, I published to a topic that all instances received. Each instance checked its local connection registry; only the instance that owned the socket sent the command.

How I validated it

I tested with multiple replicas and checked that incoming data had one persistence path while a command was sent only by the instance with the relevant connection.

Shared subscriptions remove the old duplicate-consumption behavior, but they do not create exactly-once processing. Connection changes and command acknowledgement remain separate design concerns.

Decision record: distributed consumption is not socket ownership

Failure mode

Every replica subscribed to the same incoming topic. With a single pod that was invisible; with two pods, both persisted the same packet. The fault was consumer fanout, not a database race.

Separate ownership models

Telemetry is distributable work: one eligible consumer should process each delivery. A device command is different because the TCP socket exists only in the memory of one process. A shared store can identify an owner, but it cannot transfer the live socket object to another pod.

Alternatives and trade-offs

  • Application-side coordinator: possible, but it duplicated broker functionality for ingress and introduced another routing dependency.
  • Central command process: simplified selection but created a new availability bottleneck and still needed to handle reconnect ownership.
  • Fanout with local ownership check: each pod examines a command, but only the owner writes to its socket. This matched the existing process-local connection model.

Client-library verification

The original client path dropped shared-subscription messages in a proof of concept. I checked a newer version of the same client family, confirmed the relevant limitation remained, and moved to a client that supported the subscription behavior required by the design.

Guarantee boundary

Shared subscriptions eliminate the old simultaneous fanout; they do not make processing exactly once. A stronger command guarantee would need explicit ownership discovery, reconnect handling, acknowledgement, and retry semantics.

Cost investigation · AWS S3 / CloudTrail / Athena

Finding the queries behind rising S3 API costs

A plausible first explanation turned out to be wrong. I attributed the requests to unused analytics schedules and reduced daily S3 API cost from about $138 to $6.

Situation
S3 API cost had risen sharply; a data crawler seemed like the most likely cause at first.
My role
I traced request sources through billing, CloudTrail records, Athena history, and scheduled workloads.
Key decision
Stop unused schedules after rechecking the hypothesis across a longer billing window.
Result
Daily S3 API cost fell from about $138 to $6, a 96% reduction.

Why the first answer was not enough

Changing the crawler schedule initially appeared to reduce cost, but billing data arrived with a delay. I did not treat that timing correlation as evidence of cause. A longer recheck showed the crawler was not the source of the high request volume.

How I found the source

I grouped CloudTrail events by request type and caller, then compared the result with query history. The dominant requests came from scheduled analytics queries scanning an unused table without partition conditions. The schedules had no remaining consumer, but they still generated broad storage scans.

What I changed and verified

I stopped the unused schedules and compared the same daily S3 API cost signal afterward. The cost fell from about $138 to $6 per day. This result is intentionally scoped to S3 API requests, not the whole AWS bill.

Investigation record: attributing cost before changing infrastructure

Why the first hypothesis was rejected

A crawler schedule was an intuitive suspect, and an early cost movement looked encouraging. Billing lag meant that observation was not causal evidence. I rechecked over a longer window before committing to a broader infrastructure change.

Attribution path

  • Isolate the S3 API dimension that increased.
  • Group audit events by request type and caller rather than guessing from a nearby service change.
  • Join the dominant caller back to query history and scheduled workloads.
  • Confirm whether each workload still had a consumer before optimizing it.

Decision criterion

Partitioning or narrowing the query range would reduce an active workload. These schedules had no remaining consumer, so removing them was lower risk and removed the request source entirely. I then compared the same daily S3 API cost signal after the billing delay.

Telemetry processing · Kotlin / Redis

Stabilizing battery-level readings while a vehicle is moving

A voltage-only battery reading dropped and rebounded under driving load. I implemented a state-aware filter that reduced the maximum visible drop during driving from 25 percentage points to about 6.

Situation
A noisy physical signal affected both a customer-facing value and a battery-replacement pricing rule.
My role
I tested the telemetry assumptions, implemented the filtering pipeline, and released it to production.
Key decision
Use a causal three-stage filter and separate the display value from the stopped-state value used for pricing.
Result
Maximum visible drop while driving improved from 25 percentage points to about 6.

Context and investigation

Battery level was derived linearly from terminal voltage. Driving load could lower voltage by 1–2 V, so the displayed level fell sharply and then recovered at a stop. Field data also showed that two assumptions were unreliable: helper packets were not always valid input, and speed zero did not always mean the vehicle had stopped.

What I implemented

The pipeline first clamped physically implausible values, then used a causal Hampel filter to reject local outliers without looking ahead in time, and finally applied an asymmetric EMA that responded differently while moving and stopped. Pricing used the latest stopped-state reading rather than a transient reading taken under load.

Why this shape

The filter had to run online, so it could not rely on future samples. Each stage owned a different problem—impossible values, isolated local spikes, and the response speed of a user-facing display—rather than hiding all behavior in one broad smoothing rule.

Design record: a causal filter with separate responsibilities

Why a causal pipeline

The value was calculated online, so a filter that needs future samples was not available. The pipeline therefore used only the current and prior observations. Clamping rejected impossible values, the Hampel stage compared a local value against a robust neighborhood baseline, and the asymmetric EMA controlled how quickly the displayed value could move in each state.

Options I ruled out

  • Ignore a falling value while driving: stable-looking, but it could hide a real battery drop.
  • Increase upload frequency: more samples did not correct a load-dependent measurement error and increased data volume.
  • One symmetric moving average: simpler, but it lagged genuine changes and did not distinguish moving from stopped behavior.

Why display and pricing diverged

A display can be smoothed for readability. Pricing needs a value that is defensible for the business rule. Reusing a transient moving-state voltage reading for both would couple two goals with different error costs, so pricing used the latest stopped-state reading instead.

Verification

I compared before-and-after driving traces, then separately checked the stopped-state value consumed by pricing. The target was not a smoother chart alone: it was a stable display without converting every low reading into an invalid sample.

PRODUCTION NOTES

Backend work, with the hard parts included.

01

PAYMENTS · STATE & RECOVERY

Payment state must survive an unclear provider response.

The payment flows I worked on involved multiple payment methods and asynchronous provider outcomes. The important choice was to make the payment lifecycle explicit, rather than assuming a synchronous response tells the whole story.

CLIENTRequest or retry
→
PROVIDERResponse may be delayed or lost
→
PAYMENT STATEOne guarded transition
←
ASYNC PATHSCallback or inquiry

Implemented / investigated

  • Used explicit intermediate and terminal states instead of interpreting a client timeout as a failed payment.
  • Handled repeat requests idempotently around payment changes.
  • Processed asynchronous callbacks and used a later inquiry path for unresolved provider outcomes.
  • Supported a regional rollout of tipping payments.

Ownership boundary

The customer-facing business change and the provider transaction are related, but not the same record of truth. I keep a stable external reference and apply callback or inquiry results through controlled internal transitions.

Failure cases the flow has to answer

Same request againA repeated client submission is matched to the logical operation. It should return or continue the existing work, not start a second provider operation.
Provider completed; caller timed outThe caller stopping its wait does not establish provider failure. Keep the operation unresolved until an inquiry or callback supplies a definitive outcome.
Callback arrives twice or lateUse the stable provider reference and make terminal transitions idempotent. A replay must not capture twice or move a completed payment backward.
Work cannot be processed nowRetry, DLQ, and idempotency are separate tools: delivery retry, isolation for manual/controlled handling, and safety under repeated processing.

Design direction: no-row concurrency

A row lock cannot protect a payment-change record before it exists. For a redesigned concurrent change flow, I would claim a short-lived state on an existing aggregate record, commit that decision, and call the provider outside the database transaction. This is a design proposal, not a claim about an already-shipped path.

Review questions I would expect

  • Which source is authoritative when the provider may have completed after the local timeout?
  • What is the concurrency anchor before a new payment record exists?
  • Why must a remote provider call not hold a database transaction open?
  • What prevents a late callback from changing a completed state?

02

MESSAGING · MQTT · CONNECTION OWNERSHIP

A broker can distribute work. It cannot own a socket for you.

In connected-device and mobility systems, inbound events can scale through a broker while outbound commands still have to reach the process holding a live connection. Treating those paths as the same problem creates hard-to-debug delivery failures.

INBOUNDDevice event → broker → domain consumer
↔
OWNEROne service instance holds the live connection
↔
OUTBOUNDCommand → owner resolution → device

Implemented / investigated

  • Worked on Kotlin/Spring services handling mobility and connected-device workflows.
  • Used broker-mediated distribution for independently scalable consumer work.
  • Reasoned about connection lifecycle, reconnection, duplicate delivery, and consumer lag as normal operating conditions.

The key boundary

Event consumers can be assigned work through a broker. A device command is different when the connection itself lives in one application instance. The system needs a way to resolve that owner before delivery.

Conditions to make explicit

Connection dropsThe owner record can become stale. Delivery needs a clear unavailable/retry path rather than silently treating a missing socket as success.
Event is repeatedBroker delivery is commonly at-least-once. Consumers need a stable event identity or a state transition that is safe to repeat.
Command reaches the wrong instanceRandom consumer selection is not enough for an in-memory connection. Route through owner resolution or a connection-aware delivery channel.
Backlog growsLag is an operational signal, not merely a queue detail. Measure it and distinguish slow consumers from a downstream dependency failure.

Trade-off

Keeping connection ownership in memory makes low-latency delivery straightforward, but adds lifecycle coordination. Moving every command through a central store simplifies ownership at the cost of another hop and different failure modes. The right choice depends on ordering, latency, and reconnect behaviour—not on whether a broker is already present.

Review questions I would expect

  • How does a command find the instance that owns the active connection?
  • What does success mean if the device disconnects after the command is accepted?
  • Where is duplicate delivery made safe: the broker, the consumer, or the domain state?
  • What evidence separates consumer lag from an unavailable downstream system?

03

PRODUCTION RELIABILITY · DIAGNOSIS

Use each piece of evidence for the question it can actually answer.

I have investigated production symptoms and recurring cloud usage by first narrowing the hypothesis. The goal is not to collect more logs; it is to distinguish active work, retained memory, transaction contention, and external dependency behaviour before changing code.

Implemented / investigated

  • Investigated backend reliability symptoms with runtime and application evidence.
  • Examined transaction boundaries around slow external dependencies.
  • Reduced recurring cloud API usage after tracing request origin and volume.
  • Led framework upgrades across production services.

Operating principle

Operational symptoms are ambiguous. A thread snapshot, a heap dump, a database metric, and an audit trail are useful because they rule out different explanations—not because any one of them proves the cause on its own.

Evidence map

High CPUA thread dump is only a moment in time. Use CPU sampling or accumulated CPU evidence to find sustained work; RUNNABLE alone is not proof of CPU ownership.
Heap growth / OOMUse a heap dump to inspect retained objects and reference paths. Thread state cannot establish why memory remains reachable.
Slow request with database pressureInspect transaction duration, connection-pool wait, query timing, and whether an external network call is being held inside the transaction.
Unexpected cloud costStart with audit records: principal, action, frequency, and caller. Then reduce the unnecessary work and verify behaviour over time.

Transactional boundary

A database transaction is a consistency boundary for database work; it is not a safety blanket for a remote call. Holding it while waiting on an external provider increases lock and pool pressure, while still not making that provider operation atomic. I keep the database decision short and make the remaining recovery path explicit.

Review questions I would expect

  • What observation distinguishes high allocation from retained-memory growth?
  • Why is a RUNNABLE thread not enough evidence for a CPU conclusion?
  • Which transaction boundary is necessary, and which one merely holds resources during a remote wait?
  • How do you prove a cost optimisation continues to work after the first deployment?

What I would want a reviewer to see.

I am comfortable with implementation details, but I also care about the boundaries around them: what happens when an event repeats, a provider does not answer, a connection moves, or a diagnosis is wrong. Those are the situations where careful backend design shows up.

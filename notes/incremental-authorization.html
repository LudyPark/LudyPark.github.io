Handling a fare increase after authorization

A Change of Destination could increase the final fare, but the original flow did not secure the increase before the ride ended. The resulting risk appeared at settlement: if the rider no longer had sufficient balance, the platform could recover the originally authorized amount but lose the increase. My task was therefore not simply to call another payment API; it was to improve fare recoverability without putting the original authorization at risk.

Scope: securing fare increases in Vietnam · My role: comparing options, verifying the minimum charge unit, and implementing the flow

1. The increase was unsecured until settlement

At dispatch the service authorized the estimated fare against the rider's account. A destination change raised the final fare, but the flow did not authorize the difference then; recovery was attempted at settlement. A rider whose balance had since dropped left the increase uncollectable while the original authorization stayed intact.

MoMo could not increase an existing hold, so securing the delta required a second authorization transaction, which normally adds a per-transaction fee. In the production Vietnam configuration the MoMo AOF fee rate was zero. If this design expands to a region with a non-zero rate, that trade-off must be evaluated again.

2. Two costs decided it

I compared the options by two costs: the fare left unsecured when settlement failed, and the fee created by a second authorization. With the fee at zero, preserving the original hold and authorizing only the positive delta improved the collection boundary without an incremental MoMo AOF fee in this production configuration.

3. Proving the increase is always in a chargeable unit

The provider required a minimum payment unit of 1,000 VND, so I traced every component of the fare difference (new total minus old) through code. Base fare was rounded to 1,000 before price calculation; system fee configuration in this region used the same unit and did not take the tax-addition route; percentage coupons rounded up to 1,000; unchanged components such as tolls cancelled out in the delta.

That was not a claim of a universal guarantee. Fixed-amount coupons and option-fee admin values were not constrained by the same code path, so I recorded them as operating discipline. I also confirmed that the MoMo AOF fee rate in this production region was zero. If this flow expands to a region with a non-zero rate, the trade-off needs review again.

4. Two entry points, two failure policies

The service creates a separate hold only for a positive delta and keeps the original hold untouched. It is enabled by region × payment-method configuration because gateway capabilities differ by region.

5. Settlement, and a defect I found after shipping

Each hold is captured separately, and a retry selects only holds still in the HELD state, so a successful capture is never charged twice. Completion is a monetary invariant over the aggregate: captured payments must sum to at least the final fare. That keeps partial-success interpretation inside the payment service rather than distributing state-combination logic to callers.

After deployment, I found an asynchronous failure event from a rejected additional hold could incorrectly move the whole ride to an error payment state. The event now carries whether that transaction had ever held money and its transaction identifier. Consumers ignore a failed satellite hold but still cancel a ride when the original dispatch-time hold fails. Broadening the guard to every failed hold would have been a different bug.

6. Verification

  • Verified the 1,000 VND constraint from each delta component and documented the two values code cannot constrain.
  • Checked separate capture and retry behavior for multiple holds, including partial capture success.
  • Verified that an additional-hold rejection no longer changes the ride-wide payment status, while original-hold failure still does.
  • Confirmed production configuration for VN + MoMo AOF on both routes.

7. Result

The flow was deployed to the Vietnam production region for destination changes and additional fees. For destination changes, the original authorization remains intact and the positive delta must be separately authorized before the change is accepted. This moved the recovery decision from settlement time to the point where the fare changed. It did not establish a measured improvement in bad-debt or collection rate. The 1,000 VND assumption was verified through the code-controlled fare components, while fixed-amount coupons and administrator-provided option fees remained operational constraints rather than universal code guarantees.

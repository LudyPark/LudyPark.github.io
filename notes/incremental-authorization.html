Handling a fare increase after authorization

The gateway could not increase an existing hold. A destination change or a fee added later required a new decision about how much money could become unsecured if the next provider call failed.

Scope: incremental-hold design for VN · My role: comparing options, verifying the minimum charge unit, and implementing the flow

1. What was wrong

The service already held the original fare. Releasing that hold before a new authorization completed could turn a confirmed fare into an unsecured one. I compared three real choices; one was the production behavior at the time.

OptionOperationFailure consequence
1Create a new full-fare hold, then release the old hold.Two times the fare is locked temporarily, directly conflicting with the goal of avoiding insufficient balance.
2 — selectedHold only the positive delta; capture each hold separately at settlement.Only the added amount can remain unsecured.
3 — existing behaviorCancel everything, then hold the full amount again.If cancellation succeeds and the new hold fails, the original fare has no hold at all.

2. The decision rule

I used one criterion: the maximum amount that can be left unpaid when a step fails. Option 3 exposed the full fare; option 2 exposed only the incremental amount. Payment work should be evaluated on the worst case, not the average case.

3. Constraints: the provider minimum and regional behavior

The provider required a minimum payment unit of 1,000 VND, so I traced every component of newNetPrice − oldNetPrice through code. Base fare was rounded to 1,000 before price calculation; system fee configuration in this region used the same unit and did not take the tax-addition route; percentage coupons rounded up to 1,000; unchanged components such as tolls cancelled out in the delta.

That was not a claim of a universal guarantee. Fixed-amount coupons and option-fee admin values were not constrained by the same code path, so I recorded them as operating discipline. I also confirmed that the MoMo AOF fee rate in this production region was zero. If this flow expands to a region with a non-zero rate, the trade-off needs review again.

4. Implementation

The service creates a separate hold only for a positive delta and keeps the original hold untouched. It is enabled by region × payment-method configuration because gateway capabilities differ by region.

Entry pointPayment policyReason
Destination change (COD-)Fail closed: block the change and return an insufficient-balance error when the additional hold fails.Do not raise the fare when it cannot be secured.
Toll or airport fee (FEE-)Fail open: a payment failure does not prevent trip completion.Stopping the trip costs more than the bounded risk of an unpaid toll or airport fee; this was agreed with the local PM.

5. Settlement and a defect found after deployment

Holds are captured one by one, not merged. A capture failure is isolated to that hold, but partial success is reported as failure to the caller. A retry captures only holds that are still held, so a successful one is not charged twice. The payment is complete only when the sum of captured payments is at least the final fare. This keeps the state-combination logic in the payment service instead of forcing callers to interpret every combination of two or three holds.

After deployment, I found an asynchronous failure event from a rejected additional hold could incorrectly move the whole ride to an error payment state. The event now carries whether that transaction had ever held money and its transaction identifier. Consumers ignore a failed satellite hold but still cancel a ride when the original dispatch-time hold fails. Broadening the guard to every failed hold would have been a different bug.

6. Verification

  • Verified the 1,000 VND constraint from each delta component and documented the two values code cannot constrain.
  • Checked separate capture and retry behavior for multiple holds, including partial capture success.
  • Verified that an additional-hold rejection no longer changes the ride-wide payment status, while original-hold failure still does.
  • Confirmed production configuration for VN + MoMo AOF on both COD- and FEE- routes.

7. Result

The flow was deployed to the Vietnam production region and runs for both destination changes and additional-fee routes. Previously, a re-hold failure could remove the existing hold and leave the full fare unsecured. The original hold now remains in place and only the delta is separately secured, reducing the maximum unsecured amount from the full fare to the added charge. I did not measure a before/after bad-debt rate.

Handling a fare increase after the original authorization

The trip price could increase after an initial authorization. The provider could not enlarge that existing hold, so the problem was not just calculating a difference—it was keeping a confirmed amount safe while requesting more.

Scope: payment behavior for a changed trip · My role: backend design and implementation

The failure mode to avoid

The original amount was already authorized. If we cancelled it and attempted one larger authorization, a failure on the second request could leave the rider without a valid hold for the original, already-confirmed fare. That coupled two different risks unnecessarily.

  1. original authorization
  2. +
  3. price change
  4. →
  5. authorize only the positive difference
  6. →
  7. capture each valid hold at settlement

Options considered

OptionWhat it simplifiesWhy I did not use it
Cancel and re-authorize the full amountOne final holdA failure on the new request puts the existing confirmed amount at risk.
Authorize a large buffer up frontFewer later provider callsIt reserves more than the known fare and is a poor fit when the final amount is uncertain.
Authorize only the increaseFailure is limited to the incrementRequires two references and separate settlement handling, but keeps the original hold intact.

Chosen model

I created a second authorization only for a positive delta. The original authorization remained unchanged. At settlement, the service captured each approved authorization independently and retained the relationship to the same trip payment context.

Risk boundary: a failure on the delta authorization did not invalidate the original hold. This was the central reason to accept the extra state and settlement work.

State and recovery considerations

Each authorization had its own provider reference and result. The service could therefore distinguish: original approved / delta pending, original approved / delta failed, and both approved. A timeout after sending the delta request was not treated as an immediate failure; it remained a status-reconciliation problem.

  1. load original approved hold
  2. →
  3. calculate positive delta
  4. →
  5. create delta authorization record
  6. →
  7. provider call
  8. →
  9. callback or status recovery

What I verified

  • No new authorization was made when the recalculated amount did not increase.
  • A failed delta request left the original authorization unchanged.
  • Duplicate requests could be identified against the payment context and did not create additional holds.
  • Settlement could identify and capture the original and delta amounts separately.

Result

The implementation handled a provider limitation without turning a later fare change into a failure of the original payment. The trade-off was explicit: more payment state to operate, in exchange for a smaller and safer failure scope.

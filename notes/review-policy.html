Centralizing review policy across ten repositories and five technology stacks

Ten repositories across five technology stacks used repository-level review workflows and prompts. Copying the criteria into every repository meant that one improvement required ten edits, omissions created policy drift, and a generic review prompt produced advice that was too broad to be useful. I moved the review policy to a central repository, synchronized it to the service repositories, and selected review criteria from the changed files and pull-request category.

Scope: review policy for ten service repositories · My role: policy structure, stack and category routing, sync mechanism

1. Copying the policy was the failure mode

The repositories spanned Kotlin/Spring Boot, NestJS, React, React Native, and Node.js. With workflow files and prompts held per repository, a single rule change had to be applied ten times. Any repository missed in that pass silently diverged, and divergence is not visible at review time: a weaker policy still produces review comments, so nothing signals that a repository has fallen behind.

One global prompt was not sufficient either. It became long enough to bury important checks and mixed conventions that conflicted across stacks. I kept a shared policy skeleton and separated the stack-specific rules.

2. Separating policy from execution

I treated the central repository as the policy control plane and each service repository as an execution plane. The central repository owns the review criteria; synchronized workflows and prompts run inside the service repositories. The distribution list and exclusions are explicit, so each policy change has a known target set.

  1. central policy repository
  2. →
  3. detect repository stack
  4. →
  5. inspect changed-file category
  6. →
  7. select general / SQL / migration policy
  8. →
  9. sync workflow and prompts
  10. →
  11. run repository-specific review

The skeleton of the policy is shared; only stack conventions and category-specific checks vary. Stack detection reads project files rather than repository names, so a repository is classified by what it actually contains. When detection is not confident the pipeline does not guess: it takes an unknown path and falls back to the most general profile rather than applying criteria from the wrong stack.

Execution is split by role. check-ignore is the gate that decides whether a review should run at all and which category applies; category-review performs the review with the selected criteria; a conditional SQL path handles database changes; an interactive path serves manual queries.

3. Why database changes needed their own path

SQL and migration changes were routed separately because their failure modes are not the same as application code. Application rollback is often possible by deploying a previous build; a migration may already have mutated data or changed compatibility constraints, so rollback is itself another migration.

Migration review checks index creation and locking behaviour, bounded backfills, and compatibility across application versions in a rolling deployment. A general code-review prompt would reduce those risks to style comments.

4. Three rules that came from failures

Each of these came from the automation failing in a way that looked like success, which is the failure mode that matters most in a pipeline nobody watches.

  • Multi-line suggestions were restricted to a single line, because GitHub can replace the surrounding range when applying them and alter code the reviewer did not intend to change.
  • A model alias was resolved incorrectly by the proxy and every review returned 403. The configuration now pins an explicit model version rather than an alias.
  • A missing heredoc terminator produced a workflow that reported success with an empty prompt, so reviews silently disappeared. Recovering from that made empty-prompt detection a requirement rather than an assumption.

5. Boundaries the automation does not cross

The bot posts review findings but cannot merge. It skips style preferences and low-confidence suspicions. The confidence threshold reduces noise; it does not make accepted findings correct. Human review, CI, and branch protection remain the approval path.

6. Result

A review rule is now updated once and synchronized to all ten repositories. Stack and change-category routing keeps SQL and migration checks out of generic application-code review. Review time was not instrumented, so I did not calculate a productivity improvement.

7. Remaining risks

Centralization also increases blast radius: a bad rule reaches every repository on the next sync. Versioning, staged rollout, and rollback were not implemented. The unknown fallback reduces the chance of applying the wrong stack profile, but it cannot eliminate misclassification. The next useful metric would be adoption rate by finding type, so ignored categories can be removed and findings that consistently lead to changes can be strengthened.

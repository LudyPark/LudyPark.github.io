Scaling MQTT ingestion without duplicating writes

Running a second copy of this service broke it in two ways at once. The same vehicle data was written to the database twice, and a command meant for one vehicle could arrive at a server that was not the one holding that vehicle's connection. Both problems had the same source, two device protocols the hardware forced on us, and each needed the opposite fix.

Scope: multi-pod device ingestion · My role: PoC, client-library replacement, and broker upgrade

1. Two protocols, chosen by the hardware

Off-the-shelf GPS trackers used a vendor binary TCP protocol and were identified by a device identifier; their firmware could not be changed. Vehicle telemetry was under our control and used MQTT. The result was one service with a broker-facing MQTT consumer and pod-local TCP connection endpoints.

With two replicas already running, both MQTT consumers processed the same packet and wrote it twice. For TCP commands, a Redis mapping from a device identifier to its local connection handle was insufficient: the handle only existed in one pod's memory, so another pod could locate it but could not write to its socket.

2. The client library was dropping delivered messages

MQTT shared subscriptions could distribute incoming work, but the Spring Integration implementation failed in a less obvious place. A local broker test with two subscribers showed broker-level delivery working. Once applied through Spring Integration MQTT, messages never reached the listener.

The library was silently discarding messages the broker had delivered correctly. The cause was its internal Paho client: its TopicValidator could not match a subscription such as $share/GROUP/topic against an incoming topic, so the broker delivered the packet and the client discarded it. This was the long-standing eclipse-paho/paho.mqtt.java#965 issue. Spring Integration 6.2 offered shared-client support but still used Paho; moving to 6.x also required Java 17 and Spring 6, so an upgrade did not remove the blocker.

3. Replace the client, upgrade the broker

I rewrote the MQTT receive layer on the HiveMQ client library and removed Spring Integration from that path. This meant taking responsibility for connect, reconnect, and subscription recovery. The production broker also had to change: it was mosquitto 1.4.15 while staging used 2.0.15. Shared subscriptions are a broker capability; client code alone was not enough. I confirmed that supported brokers could provide this behavior with MQTT v3 and that the upgrade preserved existing v3 clients.

For TCP control, I chose fan-out rather than a device-to-pod registry with inter-pod forwarding. A registry would need atomic ownership changes on reconnect, cleanup after pod death, and re-query/retry after forwarding failure. At the current command volume, sending one command intent to every pod cost less than making that registry correct.

Incoming MQTT traffic uses shared subscriptions. TCP command intents use a RabbitMQ fan-out exchange through Spring Cloud Stream without a consumer group, so every instance receives an anonymous queue. A pod without the socket performs one local lookup and stops. Commands are low-frequency compared with device ingestion, making duplicate delivery to pods an acceptable cost.

The shared consumers divided the traffic exactly 1:1, and their total matched the ordinary subscription. This checked both duplicate suppression and loss in the tested window.

6. Result

The service had already been running two copies, which is why the duplicate writes were visible in the first place. It now runs that way safely: incoming device data is split across copies instead of duplicated, commands still reach the one server holding the vehicle's connection, and autoscaling is free to move between one and six copies as load changes. Shared subscriptions cover two MQTT clients and five topics in production. The measurable part is the table above: 144 packets in, 144 stored, none of them twice.

7. What this does not solve

A shared subscription does not provide exactly-once processing across reconnects, acknowledgements, database writes, and retries. It can also fail silently: a broker without shared-subscription support can fall back to delivering every packet to every consumer. Duplicate device-data storage needs monitoring. Recent per-device history also belongs outside pod memory; the battery estimator stores it in Redis.

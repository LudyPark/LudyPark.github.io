Scaling MQTT ingestion without duplicating writes

Running a second copy of this service broke it in two ways at once. The same vehicle data was written to the database twice, and a command meant for one vehicle could arrive at a server that was not the one holding that vehicle's connection. Both problems had the same source, two device protocols the hardware forced on us, and each needed the opposite fix.

Scope: multi-pod device ingestion · My role: PoC, client-library replacement, and broker upgrade

1. Two protocols, chosen by the hardware

Off-the-shelf GPS trackers used a vendor binary TCP protocol with firmware we could not change, while vehicle telemetry was ours and used MQTT. One service therefore held a broker-facing MQTT consumer and pod-local TCP endpoints at once.

Those are two different problems. MQTT ingestion was work distribution: ordinary subscriptions delivered the same message to every replica, so both consumers wrote the same packet. TCP control was connection ownership: the live socket existed only in one pod's memory. Treating both as generic multi-pod issues would hide that they need opposite routing.

Redis could share a device-to-connection identifier, but it could not make the socket transferable, because the handle still referred to memory owned by one pod. A distributed registry would need atomic ownership changes on reconnect, stale-entry cleanup after pod death, and re-query or retry after forwarding failure.

2. The client library was dropping delivered messages

MQTT shared subscriptions could distribute incoming work, but the Spring Integration implementation failed in a less obvious place.

The PoC separated broker behavior from client behavior. The broker correctly distributed messages for $share/GROUP/topic, but Spring Integration's Paho client compared that subscription string with the incoming topic and discarded the delivered message before it reached the application listener. This was the long-standing eclipse-paho/paho.mqtt.java#965 issue. Spring Integration 6.2 offered shared-client support but still used Paho, and moving to 6.x required Java 17 and Spring 6, so upgrading did not remove the blocker.

3. Replace the client, upgrade the broker

Replacing the client with HiveMQ removed that blocker, at the cost of owning connect, reconnect, and subscription-recovery code directly. The production broker also had to change, from mosquitto 1.4.15 to the 2.0.15 already on staging, because shared subscriptions are a broker capability. I confirmed supported brokers provide this with MQTT v3 and that the upgrade preserved existing v3 clients.

For TCP control, I chose fan-out rather than that registry. At the command volume in question, sending one intent to every pod cost less than making distributed ownership correct.

Incoming MQTT traffic uses shared subscriptions. For TCP commands, every pod receives the intent, checks its local socket index, and only the owner sends. That trades command-count multiplied by replica-count duplicate consumption for removing distributed ownership consistency.

The command exchange uses fan-out through Spring Cloud Stream without a consumer group, creating an anonymous auto-delete queue per instance. A consumer group would create competing consumption and could route the command to a pod that did not own the socket, so per-instance queues deliberately replicate the intent.

A publisher confirm proves broker acceptance and a consumer ACK proves completion at the broker-consumer boundary. Neither proves a physical device executed the command. Surviving a reconnect window would need command-level state such as PENDING → SENT → ACKED, an expiry policy, device acknowledgement, and retry-safe semantics; Redis Streams or a durable queue alone would not create that execution truth.

5. Verification

The broker-level PoC established that shared subscriptions assign a message to one subscriber. Repeating that boundary test through Spring Integration exposed the client-side discard, and the HiveMQ implementation passed the same path. After rollout the live path no longer produced the duplicate writes seen with two replicas. This does not establish end-to-end exactly-once processing across acknowledgements, reconnects, commits, and retries.

6. Result

The service had already been running two copies, which is why the duplicate writes were visible in the first place. Correct ingestion no longer depends on running exactly one replica: incoming device data is distributed across consumers instead of duplicated. For a currently connected device, the command intent is broadcast so that the pod holding the live TCP socket can send it. Shared subscriptions cover two MQTT clients and five topics in production.

7. What this does not solve

Shared subscriptions do not guarantee exactly-once database processing; reconnects can still cause loss or duplication depending on QoS, session, acknowledgement, and commit timing. Fan-out is a fast routing path for connected sockets, not durable command execution: commands issued during a reconnect window can be lost, stale mappings can survive a pod crash, and anonymous auto-delete queues are not a command store. Broker and RabbitMQ failures remain separate domains.

The telemetry subscription used MQTT QoS 0, so shared subscriptions changed work distribution rather than delivery durability. Even QoS 1 or 2 would only strengthen the client-broker delivery contract; consumer idempotency would still be required around the database write. The mechanism also rests on a topic-string convention that the broker and the client must read the same way, and a mismatch there surfaces as changed behavior rather than an error. That is how the client-library problem above stayed invisible until the data was checked, so duplicate device-data storage is worth monitoring directly. Recent per-device history also belongs outside pod memory; the battery estimator stores it in Redis.

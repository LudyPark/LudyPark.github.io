Scaling MQTT ingestion without duplicating writes

Adding a replica fixed neither of the two ownership questions in this service: who should process an incoming packet, and which pod owns the TCP socket needed to send a command to a vehicle?

Scope: device packet ingestion and command delivery · My role: design validation and implementation

What broke at two replicas

The service consumed MQTT packets and also kept local GPS TCP sockets. With two pods subscribed in the ordinary way, both could receive the same inbound packet and write it to the database. A single scaling choice could not solve the outbound side either: only the pod holding a particular socket could actually send a command through it.

  1. MQTT broker
  2. →
  3. one ingest consumer for a packet
  4. →
  5. database write
  6. ↔
  7. local socket owner sends vehicle command

Two message types, two routing rules

TrafficRouting choiceReason
Inbound device packetsMQTT shared subscriptionOne eligible consumer receives a packet, preventing both replicas from doing the same write.
Outbound command intentBroadcast / fan-out to podsThe pod that owns the local socket is the only one that can execute the send; it must receive the intent.

Shared consumption was appropriate for work that only one replica should process. It was deliberately not used as a shortcut for connection ownership. A broker can distribute a message; it cannot transfer an in-memory socket from one process to another.

Client-library validation

An initial client proof of concept did not reliably deliver shared-subscription messages under the needed behavior. Because this was on the critical ingest path, I did not treat a locally successful connection as sufficient. I switched the integration to a client library that supported the required shared-subscription handling and validated delivery in the multi-pod setup.

Implementation shape

  1. ingest topic through shared subscription
  2. →
  3. one pod parses and persists
  4. →
  5. command event fan-out
  6. →
  7. each pod checks its local socket map
  8. →
  9. owner sends

The command handler did not assume it owned every connection. Each pod checked the sockets it held locally and acted only when it found the target connection. This kept the responsibility for a live TCP connection in the process that actually owned it.

What I checked

  • With multiple replicas, a single inbound packet was processed by one eligible consumer rather than written twice.
  • A command intent reached the pod that held the live vehicle socket.
  • Connection changes and reconnects remained separate from broker-level message distribution; the routing model did not claim to solve them automatically.
  • The selected client behaved correctly for the shared-subscription path in the deployment topology.

Limit and next design question

Shared subscription avoids duplicate consumption; it is not an exactly-once guarantee across reconnects, acknowledgements, database writes, and retries. A stronger design would make device ownership discoverable and treat handover, expiration, and retry semantics as explicit state. That is a different problem from distributing one incoming MQTT message.

Result

The service could scale inbound processing without duplicate database work while preserving the local ownership required for socket-based commands. The important change was not a generic “scale out” switch—it was using different delivery semantics for different kinds of ownership.

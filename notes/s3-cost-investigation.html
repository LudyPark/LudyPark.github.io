Finding the workload behind an S3 API-cost spike

S3 API cost reached $138 per day. Cost Explorer showed which S3 API category was expensive, but not which workload generated the calls, and CloudTrail principal attribution was misleading because Athena could operate through delegated Lake Formation permissions. The investigation therefore became an attribution problem rather than a storage-optimization problem.

Scope: cloud-cost investigation · My role: CloudTrail caller attribution

1. $138 a day in S3 API calls

From one day's CloudTrail record, about 168 million events, I grouped activity by event type and identified roughly 2.08 million ListObjects calls in the data-lake bucket. This was request-count billing, not scan-volume billing; List-class requests cost about twelve times Get-class requests under the historical pricing used in this investigation. Changing data format to reduce Athena scan cost would have addressed a different bill.

2. A first hypothesis that looked successful

I suspected a Glue crawler and changed its interval from one hour to four. Daily cost fell from $138 to $75. A teammate pointed out the 24–48-hour billing aggregation delay, which meant the immediate change could not establish causation. I withdrew that attribution and reprocessed 30 days of CloudTrail using userAgent rather than principal.

3. Why the first attribution was wrong

Athena could call under delegated Lake Formation permissions, which made the CloudTrail principal appear as a Lake Formation service role. By principal alone, the traffic looked like Glue-related work. The record itself was fine; I had grouped it by the wrong axis.

4. Re-aggregating the same data

I reprocessed 30 days of CloudTrail by userAgent instead. Athena accounted for 29.61 million calls and Glue for 5,516. I used local jq streaming to extract the necessary fields to line-delimited data, then sorted and counted it. Querying CloudTrail through Athena would have been possible, but adding Athena scans while investigating an AWS-cost incident was a cost I did not want to introduce.

5. The actual source

I matched StartQueryExecution timestamps and query execution IDs to the windows of ListObjects activity. Five scheduled Redash queries were producing 70,000–120,000 calls per hour. Their predicate was:

WHERE '2022-07-19' <= dt

The predicate was written against the partition column but behaved like a broad historical range on every run rather than an incremental window, so the queries repeatedly enumerated a large S3 prefix. Before removing the five schedules, I confirmed that the target table had no active consumer, verified that the query-author account was inactive, and agreed on the removal with the operations team. This separated technical attribution from the authorization to disable a production workload.

6. Verification

  • Checked request attribution by both principal and user agent; the disagreement exposed the delegated-permission attribution trap.
  • Matched scheduled query executions to the relevant ListObjects windows.
  • Observed the cost across a complete enough billing interval rather than crediting a short-lived change.
  • Confirmed that the target table had no active consumer before disabling schedules.

7. Next time

Removing the five jobs addressed the immediate cost, but the structural issue was schedules with no owner. The next controls would be workgroup scan limits and an owner field for scheduled queries.

8. Result

S3 API cost fell from $138 per day to $6 per day: a 96% reduction within that cost category. The figure refers to S3 API cost, not total AWS spend or Athena scan cost. What made the removal safe was knowing exactly which workload was making the calls, confirmed over a full billing window rather than an immediate before-and-after point. Workgroup scan limits and an owner field for scheduled queries are proposed preventive controls rather than part of the completed fix.

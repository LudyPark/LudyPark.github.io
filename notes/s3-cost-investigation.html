Finding the workload behind an S3 API-cost spike

The first apparent explanation was wrong. The useful work was attributing requests to a caller before changing infrastructure, then waiting long enough to confirm the billing effect.

Scope: cloud-cost investigation · My role: evidence gathering, caller attribution, and remediation

The signal

S3 API cost had risen to about $138 per day. A sampled log window contained a very large volume of S3 activity, including roughly 2.08 million ListObjects calls. The cost category did not identify the workload by itself, so I treated the first suspect as a hypothesis, not a conclusion.

Why the first answer was not enough

A data-catalog crawler was initially a plausible source. After changing that configuration, an early partial billing read appeared to show improvement. I did not stop there: billing aggregation lag meant a short observation window could easily credit the wrong change.

I compared caller identity in the event data instead. The crawler accounted for only a small fraction of the relevant requests, while Athena-originated activity dominated. That shifted the investigation from bucket configuration to the workloads issuing scans.

Change made

I removed the five unused scheduled queries. Their repeated scans had no active consumer and no partition condition to limit the work. The change was intentionally narrow: it removed proven waste rather than changing the storage layout or disabling unrelated data tooling.

How I validated the conclusion

  • Compared the before/after billing trend over a longer window rather than relying on an immediate partial result.
  • Confirmed that the request pattern matched the scheduled queries identified in the attribution step.
  • Checked that no active workload depended on the unused table before removing schedules.
  • Kept the distinction between the initial crawler hypothesis and the confirmed query source in the investigation record.

Method takeaway: a cost graph tells you where to look, not what to turn off. Request attribution and a complete billing window were necessary to make the change defensible.

Result

The S3 API cost fell from roughly $138 per day to roughly $6 per day, a 96% reduction for that cost category. This is not a claim about the entire cloud bill; it is the measured outcome for the S3 API-cost spike investigated here.

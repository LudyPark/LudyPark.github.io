Adding four payment methods without breaking one-tip-per-ride

The tip flow was already running in production under one rule: a ride can have exactly one tip. Break it and you either charge a rider twice or pay a driver twice. My job was to add four new ways to pay, which meant working inside a correctness design I had not written, and finding that each payment provider disagreed about what a failed payment leaves behind.

Scope: four payment methods across two regions · My role: gateway integration, and three payment-correctness fixes

1. What I had to preserve

The flow had already processed roughly 56,000 tips. One tip per ride was enforced by a unique database constraint. A short lock kept two simultaneous requests from doing duplicate external work, and a separate guard stopped a tip from merging into a fare that was already being finalized.

None of that was my design. It was the set of rules I had to keep true while adding an in-house wallet, a mobile wallet, and two bank-account methods across two regions.

2. The gateways did not agree on failure

Each method returned a different kind of answer, and each difference landed somewhere in the flow.

MethodWhat the request path gets backWhat that forced
Mobile walletSuccess or failure arrives asynchronously, on a callback.The request cannot decide the outcome. The tip stays pending and converges when the callback lands.
Bank walletA synchronous result, but a declined attempt left its record behind.The one-tip-per-ride rule then read that record and blocked the retry. Found after release.
In-house walletA direct balance operation, with no external round trip.The operation being called had to actually move money, not only verify that it could.
CardA synchronous capture against a payment method the rider picks.The selected method has to be confirmed as the rider's own before it is charged.

Shipping the first of them is where the work actually started.

3. What shipping the wallet method exposed

The in-house wallet went out first, and a report followed: riders were seeing a successful tip while their wallet balance sat untouched.

A charge that did not charge

I had wired the path to an operation that, for accounts outside a legacy bank integration, verified the balance was sufficient and then returned without moving money or writing a transaction. The caller read that empty result as success. The same call also hard-coded its transaction channel to the ride channel, so a tip that did go through was recorded as fare.

I moved the path to the capture operation and made the channel a parameter.

That closed the report. It also told me the path deserved a full read instead of one patch, and two more things came out of that.

An identifier doing two jobs

The balance service decided whether an incoming request was a repeat by reading the field that records which ride a transaction belongs to. There was no separate idempotency key in the contract. That had been survivable while a ride produced one payment; a tip makes a second. So tip charges passed a prefixed string into the ride field, and the transaction was filed against the prefix rather than the ride, while other server paths read that same field expecting a real ride.

I added an explicit idempotency key to the shared contract, passed the prefixed value there, and returned the ride field to the plain ride, through the client, the gRPC helper, and the protocol definition. Deduplication itself had been working, since the server fell back to that field. What suffered was everything downstream, including recovery code that had to query both forms.

A completion check that passed on nothing

The post-payment step asked whether every returned transaction was paid. In Kotlin, all returns true for an empty list, so a response containing no successful payment satisfied the condition, and the flow went on to mark the tip paid and credit the driver. This one dated back to the original implementation, about a year before I touched it.

I added an emptiness check in front of the condition. I found it by reading rather than from a report, so I cannot claim it fired in production, but a completion check that passes on zero payments is wrong either way.

4. The next report, and what it actually was

A report came in saying that tipping was failing across every payment method and every region. A hotfix was being discussed on that basis.

The real failure was narrower: a rider declined for insufficient balance could not tip again afterwards. The declined attempt had left a record, and the one-tip-per-ride rule read that record and refused the retry. That behaviour belonged to one gateway; the others either released the record or never wrote one. I said so, and stated plainly that whatever this was, it was not duplicate charging, which is the failure that would have justified a hotfix.

A second report that week attributed a failure to a provider the region in question does not use. The two providers fail differently, so that attribution decided where debugging would start.

With the scope corrected, severity moved from high to medium and into the next sprint. I shipped the fix the same day: the declined tip transaction is now cancelled, so a retry is free to proceed.

5. Verification

  • Before release, checked each region's payment methods end to end: that a tip was actually charged, that its transaction was readable an hour later, and that the card-gateway paths produced correct transaction data.
  • Release verification included real-card testing against the live gateway.
  • Covered ownership of an explicitly selected payment method with tests: a rider can tip with an account they own, and cannot with one belonging to another rider or to another corporate account.
  • Traced reported failures against payment records rather than the app's display state, which is what separated a real failure from a misattributed one.

6. Result

Four payment methods now handle tips across two regions. One defect was mine and a report caught it; reading the path afterwards turned up two more on code every payment method shares: an idempotency key missing from the service contract, and a completion check that had been treating zero payments as fully paid since the original implementation.

The second report is the one I would point to. Narrowed from "all methods, all regions" to a single gateway, and out of hotfix territory, before anyone started building a fix for the wrong thing.

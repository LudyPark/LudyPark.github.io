Adding tips without duplicate charges

A ride could have one tip record. The request could arrive before fare finalization, after finalization, or again after an uncertain provider response, so that invariant had to survive more than one request path.

Scope: production tip flow · My role: duplicate and failure-path design

1. The invariant

A unique database constraint keyed by the ride ensures one tip per ride. This is the durable final check. It is not enough by itself to make concurrent provider calls cheap, so the flow uses two locks for two different races.

LockRace it handles
Short Redis lock keyed by the ride, 30-second timeoutTwo requests attempting the same tip at the same time.
Separate finalization guard for the rideA tip trying to merge while the fare is being finalized. The fare-finalization route releases this lock in finally.

These locks reduce duplicate external work. The unique index remains the final guard for the one-tip-per-ride rule.

2. When a tip can merge with the fare

A tip is merged into the fare payment only when all three conditions hold: the payment method has not changed, fare payment is waiting to be finalized, and the finalization lock is acquired. Any other combination creates a separate tip payment. This reflects the state that already exists in the payment service; it does not introduce a new payment state.

3. Why the idempotency key excludes amount

The gateway idempotency key is stable for a ride and deliberately excludes the tip amount. If a rider changes the amount and submits again, including amount in the key would turn that into a new payment identity and could violate the one-tip-per-ride policy. The same key covers driver-balance credit through successOnDuplicate = true and retry handling, tying one charge to one payout.

4. Recovery after an uncertain response

A tip can have been merged into the fare, so looking only for a separate tip transaction is not sufficient. Recovery checks whether the payment total covers fare plus tip. If payment is already complete, the service finishes any missing follow-up work and blocks the duplicate request rather than sending another provider call.

The persisted payment reference distinguishes the paths: no separate reference means the tip was merged into the fare; a separate reference means it was charged independently. Settlement, refunds, and fee handling use that distinction. The platform absorbs the tip transaction fee because deducting it from the driver share would make the amount shown to the rider differ from the amount delivered to the driver.

5. Verification

  • Checked that concurrent requests cannot create a second tip for the same ride.
  • Checked that finalization and merge requests are serialized by the finalization lock.
  • Verified that a changed tip amount still resolves to the same payment identity.
  • Verified recovery for merged and separate-payment cases, including duplicate callback and response-loss paths.

6. Result

This flow has processed about 56,000 tips in production (service throughput, not an individual performance metric). It supports requests before and after fare finalization without creating a second tip record for a ride across retries, duplicate callbacks, and lost responses. The gateway leg is not exactly-once; uncertain responses converge through status lookup and callbacks.

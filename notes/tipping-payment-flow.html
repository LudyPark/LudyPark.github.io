Adding four payment methods without breaking one-tip-per-ride

The tip flow ran under a monetary invariant: one ride can produce at most one successful tip. Violating it could charge the rider twice or credit the driver twice. The existing design used a database unique constraint as the final correctness boundary, with a short lock to reduce simultaneous side effects and a separate guard around fare finalization. My work was to preserve that invariant while adding four payment methods whose completion and failure semantics were different.

Scope: four payment methods, two regions · My role: gateway integration, a payment-contract change, and the failure paths

1. The rule I had to keep

The invariant lives in the database, not in application logic:

-- Simplified; internal identifiers omitted.
CREATE UNIQUE INDEX ON tip_log (ride_id);

Two guards sit in front of it. A short distributed lock narrows the window in which two requests run the same external side effect, and a separate guard stops a tip from merging into a fare that is already being finalized. Neither is the correctness boundary: the lock reduces concurrent side effects, and the unique index is what rejects the second write. That design predates this work. The job was to keep it true while connecting an in-house wallet, a mobile wallet, and two bank-account methods.

2. Each provider answers failure differently

This is where the difficulty actually lived. Each method returns a different kind of answer, and each difference lands somewhere in the flow.

MethodWhat the request path gets backWhat that forced

The difference was not only API shape. A synchronous decline, an asynchronous callback, and a direct balance mutation create different payment-state transitions. The request path could finalize synchronous methods immediately, but callback-based methods had to remain pending until the provider supplied an authoritative outcome.

3. What I changed on the shared path

Connecting the methods was the small part. Making them safe took three changes to code that every payment method runs through.

The wallet path verified money instead of moving it

After the first wallet release, a report showed riders getting a successful tip while their balance sat untouched. The path was calling an operation that, for accounts outside a legacy bank integration, checked that the balance was sufficient and returned without charging or writing a transaction, and the caller read that empty result as success. The same call recorded any charge that did go through under the fare channel. I moved the path to the capture operation, which always moves the money, and made the channel a parameter so a tip is recorded as a tip.

One field meant both "which ride" and "seen this before"

The existing contract conflated two different concepts: the business reference that associates a transaction with a ride, and the idempotency key that identifies a retried operation. That was survivable while a ride produced one payment, but a separate tip created a second monetary operation. Tip charges pushed a prefixed string into the ride field, so the transaction was filed against the prefix while other server paths read that same field expecting a real ride. I split the two concepts across the client, the gRPC helper, and the protocol definition so retry detection no longer corrupted the ride association. Deduplication had been working before the change, because the service fell back to the reference field when no key was supplied; what it cost was every downstream reader of that field.

A completion check passed on zero payments

While reading the whole path after the wallet fix, I found a completion check that dated back to the original implementation. Kotlin's all follows the logical rule of vacuous truth: it returns true for an empty collection. In a payment-completion check, that mathematically valid behavior was an invalid business result, because zero successful payments could be treated as fully paid and the flow went on to credit the driver. An emptiness guard now sits in front of that condition.

5. A report said everything was failing

A report arrived claiming tips were failing across every payment method and every region, and a hotfix was being discussed on that basis. The payment records said otherwise. The failing case was a rider declined for insufficient balance who then could not tip again: the declined attempt had left its record, and the one-tip rule read that record and refused the retry. That behaviour belonged to one bank-wallet gateway; the other methods either released the record or never wrote one. It was also clearly not duplicate charging, which is the failure that would have justified a hotfix. A second report that week blamed a provider the region in question does not use, so I corrected that attribution before anyone debugged the wrong integration.

With the scope corrected, severity moved from high to medium. I shipped the fix the same day: the declined transaction is now cancelled so a retry can proceed, and the unique constraint still rules out a second successful tip.

6. Verification

  • Before release, checked each region's payment methods end to end: a tip was actually charged, its transaction was readable an hour later, and the card-gateway paths produced correct transaction data.
  • Release verification included real-card testing against the live gateway.
  • Covered ownership of an explicitly selected payment method with tests: a rider can tip from an account they own, and cannot from one belonging to another rider or another corporate account.
  • Traced reported failures against payment records rather than the app's display state, which is what separated a real failure from a misattributed one.

The database constraint prevents two successful tip records for one ride, but it does not by itself make every external gateway call exactly once. Callback loss still requires status lookup or reconciliation, and an idempotency key is only as strong as the boundary that enforces it.

7. Result

Four payment methods handle tips across two regions. Measured after the release, the flow has processed about 56,000 tips. That figure describes the volume carried by the resulting path, not individual productivity. The code every method shares also came out stronger: an explicit idempotency key in the payment contract, a completion check that no longer passes on empty results, and a wallet path that only reports money it actually moved.

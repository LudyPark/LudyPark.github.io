Adding tips without breaking the existing payment flow

A tip looks like a small amount change. It is not the same operation when the main fare is still open versus when it has already been finalized with the provider.

Scope: product change in an existing payment service · My role: backend implementation and failure-path design

What changed

The service already had a fare-payment lifecycle. A tip could arrive while the main payment was still being finalized, or after it had reached a terminal provider state. Treating both as one update would either create an invalid provider request or blur the accounting boundary between fare and tip.

  1. tip request
  2. →
  3. is main payment final?
  4. →
  5. combine before finalization or create a separate payment
  6. →
  7. provider callback / recovery

Constraints that drove the design

  • The original fare and the tip needed separate records and fee calculations.
  • Provider state, not only our local request time, determined which operation was still valid.
  • A client retry, a duplicate callback, or an uncertain provider response could not create two tips.
  • The flow had to remain understandable during settlement: an operator should be able to see whether a tip was part of the fare or a later charge.

The decision

When the request arrivedChosen behaviorReason
Main payment not finalAdd the tip to the in-progress payment only when that method and provider flow supported it.One final operation was still possible; there was no reason to create an avoidable second charge.
Main payment already finalCreate a new payment for the tip.The original provider operation could no longer be safely changed. Keeping the tip separate preserved a clear accounting boundary.
Provider result uncertainKeep the payment pending and recover from provider status or callback data.Retrying a create request blindly risks charging twice.

How duplicate protection worked

I used a short Redis distributed lock to narrow the window where identical requests could execute concurrently. The lock was not the final correctness boundary: the database uniqueness rule was still the durable guard. The provider reference and payment state were persisted so that a retry after an unknown response could be reconciled instead of treated as a new request.

Important boundary: the lock reduced concurrent work; it did not make an external provider call exactly-once. A timeout or lost response still required status lookup and callback-based recovery.

Implementation flow

  1. validate tip and fare state
  2. →
  3. acquire short lock
  4. →
  5. create or find durable tip record
  6. →
  7. call the valid provider operation
  8. →
  9. persist callback / reconciliation outcome

The service kept tip records separate from the fare and did not fold their fees into the fare calculation. This made the behavior explicit for both pre-finalization and post-finalization paths.

What I checked

  • A repeat request returned the existing in-progress or completed tip instead of creating another charge.
  • Two simultaneous requests could not both create durable tip records.
  • A delayed callback could update the correct record without reopening a completed fare.
  • An unknown provider response remained recoverable through its stored reference instead of immediately failing or retrying as new work.

Result and remaining limit

The feature supported both product timings without changing the meaning of the original fare payment. It also made later support and reconciliation easier because the payment model recorded which path had happened. Delivery still depended on provider callbacks and recovery queries; the implementation did not claim exactly-once delivery across the network boundary.

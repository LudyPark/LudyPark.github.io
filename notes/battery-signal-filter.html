Making battery state useful under driving load

A battery value used in a customer-facing, price-sensitive flow could not jump down under acceleration and rebound after stopping. The raw voltage was responding to load, not only to stored energy.

Scope: device signal processing in a production service · My role: analysis, filter design, and implementation

Why the raw value was misleading

During driving, load could produce a one-to-two-volt terminal-voltage drop. A simple voltage-to-state-of-charge conversion made that temporary drop visible as a large loss of battery state, then showed a rebound after the load changed. This was not just a dashboard problem: the value was used in a price-sensitive replacement flow.

Field observations also invalidated two convenient assumptions. A helper packet was not reliable enough to treat as ground truth, and a speed value of zero did not always mean the vehicle was genuinely stopped.

Requirements for the filter

  • It had to run online, without looking ahead at future samples.
  • It needed to reject isolated spikes without freezing a genuine trend.
  • Downward movement during load needed more damping than recovery, because the raw signal's error was asymmetric.
  • The value chosen for the price-sensitive path needed a stricter condition than merely observing a transient zero speed.

Design chosen

StageResponsibilityWhy it belongs separately
ClampKeep an input inside a valid SOC range.Prevents invalid values from contaminating later calculations.
Causal Hampel filterDetect a local outlier from recent history.Uses only prior samples, so it can run in the live path.
Asymmetric EMASmooth normal movement with different response for decline and recovery.Models the observed load-induced downward bias without hiding every change.

I kept these responsibilities separate instead of putting every rule into one threshold. It made it possible to ask whether a bad result came from an invalid input, an isolated outlier, or normal-but-noisy movement.

Why asymmetric smoothing

A symmetric smoother treats a sharp drop and a rebound as equally trustworthy. In the observed driving behavior, that was not true: the sharp drop was often voltage sag under load. The implementation used more resistance to that direction while allowing recovery to converge at a different rate. The choice was based on the signal behavior, not on a generic preference for smoothing.

How the product value was selected

The service maintained the processed stream for display and used the latest value that met the real stopped-state criteria for the price-sensitive path. The distinction mattered: a stream can be useful for visibility while still requiring a stricter selection rule when it affects a customer outcome.

Validation

  • Compared filtered output with representative driving segments where raw voltage sag had previously caused a visible drop and rebound.
  • Checked that the filter did not require future samples, which would make it unsuitable for live processing.
  • Tested boundary and outlier behavior separately from normal gradual battery change.
  • Verified that pricing selected a stopped-state value rather than a transient measurement during motion.

Result

The maximum visible driving drop in the affected pattern improved from about 25 percentage points to about 6 percentage points. The work did not make voltage a perfect measure of battery state; it made the live value stable enough for the product behavior that depended on it.

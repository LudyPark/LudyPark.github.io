Tracing recurring pod restarts to transaction scope

A service that ingests data from vehicles in the field began restarting every three to five minutes after a deployment. Doubling its memory limit changed nothing; it grew past the new limit too. Meanwhile the vehicle data kept arriving, and the service kept falling further behind it.

Scope: production incident · My role: thread-dump analysis and transaction-scope separation

1. More memory did not help

The container memory limit was raised from 4 GiB to 8 GiB, but memory still grew beyond 10 GiB. The useful question was why throughput was falling while packets kept arriving, rather than how much more heap the process could hold.

2. Why I read thread dumps first

The symptom was “slows down, then dies,” so I investigated what was consuming time before investigating what had accumulated. A heap dump would show waiting request objects, the effect of the queue, not necessarily the work that created it.

One packet-processing thread spent 8.5 seconds in PgConnection.getTransactionIsolation() and appeared RUNNABLE. That state alone was not proof of CPU work: socket reads can also appear runnable because the JVM cannot distinguish native I/O blocking. I used accumulated CPU alongside thread state to locate the expensive work.

3. An error report was holding a database connection

  1. packet DB work + Sentry reporting in one transaction
  2. →
  3. recursive reflection serialization
  4. →
  5. connection held for 30–40 seconds
  6. →
  7. HikariCP waits
  8. →
  9. requests accumulate in heap

The packet use case performed DB work and Sentry reporting inside the same transaction. Sentry's JsonReflectionObjectSerializer recursively serialized an attached object graph without caching. The thread dump showed the same stack pattern repeatedly and 33,745 ms of accumulated CPU on the relevant thread; this was accumulated CPU, not the duration of one serialization call.

Transactions that normally lasted around 10 seconds stretched to 30–40 seconds while retaining a DB connection. The HikariCP pool had 15 connections, and the dump showed 34 requests TIMED_WAITING for a connection. Ingress continued, so queued request objects accumulated until the pod restarted.

4. Why more memory or a larger pool could not fix it

Serialization pushed processing throughput below ingress throughput. When arrivals exceed processing, the queue grows without bound regardless of memory or pool size; those changes only delay the failure. I also could not reproduce the incident locally because the trigger depended on production data shape. That made serialization-tuning ideas hard to validate, so I chose a change that structurally capped transaction time instead.

5. Move the report outside the transaction

The transaction now returns alerts as a value after DB work. An outer orchestrator sends those alerts after the transaction has completed. The transactional method lives in a separate bean, because self-invocation would not pass through Spring's proxy, and makes its contract explicit:

// transaction ends before external alert delivery
fun handlePacket(packet: DevicePacket) {
  val alerts = transactionalProcessor.process(packet)
  sendAlerts(alerts)
}

@Transactional(isolation = Isolation.READ_COMMITTED, timeout = 20)
internal fun process(packet: DevicePacket): List<Alert>

Alerts are returned as typed alert values, not strings. A send failure is caught and logged without extending or breaking packet DB processing. Repeated reporting was also reduced.

6. Verification

  • Observed restarts stop and Grafana memory settle near 2.4 GiB, similar to the pre-incident level.
  • Checked that the transaction once again covered DB work rather than external serialization and network reporting.
  • Checked the incident chain against thread CPU, connection waits, transaction duration, and memory trend instead of treating any one metric as proof.

7. What this change does not guarantee

If the DB commit succeeds and the process stops before alert delivery, an alert can be lost. That was acceptable for this monitoring side effect. For mandatory delivery, I would persist an outbox row in the same transaction and have a separate worker retry it; that is a later design option, not the incident fix.

8. Result

Restarts stopped and memory settled around 2.4 GiB, close to where it sat before the incident. What matters more than the number is the shape of the fix: external reporting can slow down again without taking database connections with it, so the same chain cannot rebuild the backlog that was killing the service.

Tracing recurring pod restarts to work inside a transaction

Increasing the pod memory did not stop the restarts. The useful question was not “what object is large?” but “what work is holding the system up long enough for traffic to accumulate?”

Scope: production incident after deployment · My role: investigation, mitigation, and follow-up change

Initial symptoms

After a deployment, pods restarted roughly every three to five minutes. Raising the memory limit from 4 GiB to 8 GiB did not stabilize the service; a pod continued to grow past 10 GiB. The traffic path accepted device packets and used database connections during processing, so a restart was the end of a longer back-pressure chain, not necessarily the first failure.

What I investigated

I started with the restart pattern, memory trend, thread samples, and database-pool pressure rather than assuming a conventional heap leak. Repeated thread observations pointed to the error-reporting SDK spending about 33 seconds serializing a large attachment/object graph through reflection. The serialization was triggered repeatedly by the same error condition.

That report happened inside the database transaction. A transaction that was normally around 10 seconds could remain open for roughly 30–40 seconds. With a pool of 15 connections, incoming packet work began waiting; those waiting requests accumulated in memory and eventually the pod was killed.

Change made

I reduced the repeated reporting trigger and moved the external error-reporting work outside the transaction. The transaction could complete without waiting on serialization and a network-bound external SDK. This addressed both multipliers in the chain: fewer repeated reports, and no longer holding a database connection while producing one.

Why this was the smallest safe change: increasing the pool or memory would have only delayed saturation. Removing the work from the critical path shortened resource ownership at the point where the queue began.

Validation

  • Tracked pod memory and restart behavior after the change; memory stabilized around 2.4 GiB.
  • Checked that transaction duration and database-pool pressure returned to a sustainable level.
  • Verified that repeated error conditions no longer produced the same volume of expensive reports.
  • Kept the incident chain documented so a future memory increase would not be mistaken for the primary fix.

What the fix did not guarantee

Moving reporting outside the transaction intentionally accepted a small possibility that a completed business change would not be accompanied by an external alert if the process stopped at the wrong time. For a must-deliver notification, I would use a persisted outbox and separate worker with retry and an idempotency boundary. That was a later design option, not the production mitigation described above.

Result

The service stopped cycling through restarts and pod memory stabilized at about 2.4 GiB. More importantly, the fix restored the intended ownership boundary: the database transaction covered database work, not an expensive external reporting path.

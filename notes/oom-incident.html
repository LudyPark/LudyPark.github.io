Tracing recurring pod restarts to transaction scope

A service that ingests data from vehicles in the field began restarting every three to five minutes after a deployment. Doubling its memory limit changed nothing; it grew past the new limit too. Meanwhile the vehicle data kept arriving, and the service kept falling further behind it.

Scope: production incident · My role: thread-dump analysis and transaction-scope separation

1. More memory did not help

The container memory limit was raised from 4 GiB to 8 GiB, but memory still grew beyond 10 GiB. That was container memory, which does not prove the 10 GiB was Java heap: thread stacks, Metaspace, and direct buffers all contribute. So the investigation did not begin by declaring a heap leak. It began by asking why processing throughput had fallen below ingress.

2. Why I read thread dumps first

The symptom was “slows down, then dies,” so I looked at what was consuming time before what had accumulated. A heap dump could show the accumulated request objects and their retention paths, but it would not by itself prove which slow operation had pushed processing throughput below ingress.

One packet-processing thread spent 8.5 seconds in PgConnection.getTransactionIsolation() and appeared RUNNABLE, which is not evidence of CPU work because native socket reads look runnable too. I correlated thread state with accumulated thread CPU, repeated stack patterns, transaction duration, and HikariCP waits: that thread showed 33,745 ms of accumulated CPU while 34 requests waited for a pool of 15.

The packet use case ran DB work and Sentry reporting in the same transaction, and Sentry's JsonReflectionObjectSerializer recursively serialized an attached object graph without caching.

The trigger was not a one-time exception burst: while the same mismatch between the incoming device report and the stored records stayed unresolved, every packet produced the same alert. I reduced that repetition as well as moving delivery outside the transaction.

The transaction held its connection for that whole time, waiting requests showed as TIMED_WAITING on the pool, and ingress continued until queued objects filled the heap.

4. Why more memory or a larger pool could not fix it

Once reflection serialization pushed the service rate below the packet arrival rate, the backlog became unstable. More heap or a larger pool adds buffering without restoring the service rate, so either would only delay the next failure. I also could not reproduce the incident locally, since the trigger depended on production data shape, so serialization tuning was hard to validate. I chose a change that structurally capped transaction time instead.

5. Move the report outside the transaction

The fix changed the transaction contract rather than moving a line of code. The transactional component performs database work and returns typed alert values; a separate outer orchestrator delivers them once the proxy-managed transaction has completed. Keeping that method in another bean makes the Spring AOP boundary explicit and avoids self-invocation bypassing @Transactional. What mattered was moving external serialization and network I/O outside the transaction and the HikariCP connection lifetime.

// transaction ends before external alert delivery
fun handlePacket(packet: DevicePacket) {
  val alerts = transactionalProcessor.process(packet)
  sendAlerts(alerts)
}

@Transactional(isolation = Isolation.READ_COMMITTED, timeout = 20)
internal fun process(packet: DevicePacket): List<Alert>

A send failure is caught and logged without extending or breaking packet DB processing.

6. Verification

  • Observed restarts stop and Grafana memory settle near the pre-incident level.
  • Checked that the transaction again covered DB work rather than external serialization and network reporting.
  • Checked the chain against thread CPU, connection waits, transaction duration, and memory trend rather than treating one metric as proof.

7. What this change does not guarantee

If the DB commit succeeds and the process stops before alert delivery, an alert can be lost. That was acceptable for this monitoring side effect. Mandatory delivery would require an outbox row written in the same database transaction, a retrying worker, and an external idempotency boundary; that is a redesign option, not part of the incident fix. Increasing memory or the connection pool would only delay the same throughput collapse and would add pressure to the database's connection limit.

8. Result

Restarts stopped and memory settled around 2.4 GiB, close to where it sat before the incident. What matters more than the number is the shape of the fix. External reporting can slow down again without holding database connections, so the same HikariCP-exhaustion chain cannot recur. Slow reporting can still reduce end-to-end throughput and must be monitored separately.
